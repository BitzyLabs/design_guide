# Product Naming That Can Survive the Real World

## The Bitzy Labs founder-led naming playbook

**Maintained by:** [Bitzy Labs](https://github.com/BitzyLabs)  
**Version:** 1.0 · **Updated:** 26 October 2026  
**Audience:** Founders, indie hackers, startup teams, product marketers, and AI-assisted builders  
**Companions:** [Human-Friendly Design](human_friendly_design.md) · [AI Development & Project Management](project_mgmt.md)

> **A name isn't a random word that happens to have an available domain.** It should express the right personality, survive being spoken and searched, fit a credible brand, clear practical collision checks, and remain sensible as the product grows.

### Where this guide comes from

This is an **original synthesis of how we've explored and selected names across Bitzy Labs projects**, with the clearest documented example being **RoleRiff**, plus our broader brand-search practice, domain decisions and brand system work. This is not a universal formula, a professional naming consultancy's framework or legal/trade mark clearance.

**I'm a founder, not a professional brand strategist, UI/UX designer or developer.** AI helps explore names, research, mock up visual options and organise decisions; I set the direction, push back when suggestions feel wrong, test whether an idea has personality, and choose what feels appropriate to the product.

Names and circumstances used below illustrate our process; **nothing in this guide means those names have been professionally cleared, registered as trade marks or remain available to buy today.** Avoid sharing confidential unlaunched shortlists or commercially sensitive strategy in public.

## Start here: one prompt, with the AI doing the research

**For most founders, this is the only part you need to copy.** A connected assistant should run the discovery, competitor research, domain comparisons and registry pre-screen **itself**, then present the useful evidence and a small number of decisions. The sections below explain the quality standard and what to do when a source is inaccessible.

~~~text
You are the naming strategist and research analyst for MY product.

Follow this full product_naming.md guide. Treat BitzyLabs/design_guide as
read-only upstream, not a repo you may edit.

PRODUCT / CURRENT BRIEF: [describe the idea; if an existing project,
read my current project brief and accepted pivots]
TARGET AUDIENCE / INITIAL MARKETS: [e.g. Australian founders + global SaaS]
BRAND FEEL: [e.g. rebellious and smart; warm and no-fuss]
AVOID / EARLIER REJECTIONS: [if known; otherwise find existing naming board]
DOMAINS AND BUDGET: [.com/.au/.app/.dev; max first-year and renewal]
AUTHORIZED PROJECT REPO/NOTION: [my own location, if connected]

Work autonomously on READ-ONLY research and a proposed naming decision pack:

1. Define the actual product promise, customer, emotional territory,
   market and plausible pivots. Confirm what is already decided.
2. Research DIRECT competitors, ADJACENT/ALIGNED products and SUBSTITUTES
   based on the same customer problem and purchasing decision—not only
   matching keywords. Give real product links and evidence of what
   they actually offer. Identify how our value proposition differs.
3. Generate 3–5 distinctive naming territories, then a diverse longlist;
   eliminate generic, misleading, awkward, phonetic and rejected ideas.
4. Screen 8–12 stronger names for REAL same/similar brand use, especially
   software businesses in related markets. Mark confusing collisions
   separately from ordinary product competition.
5. Discover available registrar tools, including Composio-accessible
   integrations and direct GoDaddy / Namecheap / Spaceship / other
   supported providers. Read each tool's schema. Batch LIVE checks for
   relevant TLDs. Compare availability, first-year and renewal price,
   currency, premium pricing, taxes/eligibility and unsupported TLDs.
   NEVER invent prices; NOT SUPPORTED != NOT AVAILABLE.
6. Pre-screen 3–6 survivors through the official ASIC business-name
   register / availability checks and IP Australia TM Checker / Australian
   Trade Mark Search. Include exact, sound-alike, visual and relevant
   goods/services/class matches. Check extra jurisdictions if needed.
   If a protected portal blocks automation, say NOT VERIFIED and give me
   its official URL plus the exact final query I need to confirm.
   Never equate a domain or ASIC result with trade mark clearance.
7. Create mini brand-direction comparisons for the best 3–5 names:
   core thesis, three tone adjectives, don't-sound-like constraints,
   taglines, homepage/support copy, logo/wordmark concept, two palette
   directions and spelling/pronunciation stress tests.
8. Rank the finalists with an explained weighted scorecard, but treat
   collision/legal risks as separate blockers. Keep a durable SHORTLIST,
   WATCH/NEEDS CHECK and REJECTED/DO-NOT-RECYCLE register.
9. For a product pivot, reassess whether to KEEP / REPOSITION / EXTEND /
   RENAME the current brand. Do not assume rebranding is required.
10. Deliver one concise, date-stamped NAMING DECISION PACK:
    positioning; verified direct/adjacent competitors; names rejected;
    registrar/prices snapshot; ASIC and trade mark findings;
    brand-voice options; recommended lead, runner-up and fallback;
    evidence links; unresolved risks; next owner approvals.

Research first, without making me manually perform the whole workflow.
Batch inexpensive lookups; deepen only finalists. Do not ask many setup
questions if reasonable assumptions can be stated and checked.

NEVER: purchase/register/renew domains, file business names or trade marks,
spend money, change DNS/production/public branding, or alter another
organisation's repo without my explicit authorisation.
Do not pretend a website or government register was checked if it wasn't.
Save the decision pack only into MY authorised repo/Notion, if available.
~~~

### What the agent should return

**Deliverables in one answer or one small file set:** (a) positioning brief and naming territories; (b) dated real-competitor map with **direct, aligned/adjacent and substitute** categories; (c) longlist funnel with do-not-recycle reasons; (d) multi-registrar domain/renewal comparison; (e) ASIC/trade mark pre-screen and precise outstanding checks; (f) voice, palette and positioning options; (g) founder-ready recommendation and decision memo.

**Gate:** research is authorised; **purchases, filings, DNS and public rebrands are not**. An agent may be unable to use a government portal or an unavailable registrar. In that case it should complete the rest and hand over **only the specific final human check**, not turn the whole research process back into homework.

## 1. What our naming process actually looks like

Our strongest naming exercises follow a process that can be repeated without making all products sound alike:

~~~text
Understand product + buyer + feeling
   ↓
Write naming brief and hard exclusions
   ↓
Explore distinct naming territories
   ↓
Generate a manageable longlist with explanations
   ↓
Kill names that fail the human tests
   ↓
Check markets, similar names, domains and potential trade mark conflicts
   ↓
Promote a *few* serious finalists
   ↓
Try full brand voices, logos, palettes and real product mockups
   ↓
Re-check practical/legal issues and real purchase costs
   ↓
Founder selects and authorises registration
   ↓
Record decision, canonical spelling/domain and brand guide
~~~

**Critical distinction:** Naming research ≠ trade mark clearance. A name being memorable, a matching domain being available, or an AI saying “looks clear” does **not** establish legal rights.

### Three principles we keep coming back to

- **Brief first:** the product's market, customer frustration, energy and future scope determine what a “good” name means.
- **Personality before polish:** a gorgeous mock logo cannot save a name that's confusing, indistinctive or a poor fit.
- **A real decision needs evidence:** domains, ownership/renewals, adjacent brands and public market use are checked—not guessed.

## 2. Real naming lessons from Bitzy Labs

### RoleRiff: strong personality, multiple finalist directions

Our job-search product started with a clear emotional brief: young-ish, frustrated job seekers who were tired of stale corporate recruitment language. We wanted something **short, catchy, energetic, unusual and a little rebellious**—but still credible for a paid product.

Five serious finalists moved into deeper exploration:

| Candidate | Territory we explored | Useful lesson |
| --- | --- | --- |
| **RoleJolt** | Impact, spark, disruption | A good name can communicate movement immediately |
| **RoleRebel** | Defiance, challenging the status quo | Rebellion can be distinctive without becoming antagonistic |
| **RoleRogue** | Independence, unconventional paths | Edginess can be memorable, but raises trust/meaning questions |
| **RoleRiff** | Improvisation, tailoring, creativity | A suggestive name can carry story and tone beyond a literal feature |
| **RoleSpry** | Agility, intelligence, nimbleness | A short word can feel friendly and capable without sounding corporate |

This was **not** simply a “pick the highest numerical score” exercise. We explored slogans, brand voice, several logo directions and multiple palette systems. The finalists were tested as potential **landing pages, app icons, social ads, onboarding and pricing experiences**, not as isolated words. Early logo sketches were deliberately treated as exploration, **not legally cleared production marks**.

**RoleRiff** was eventually adopted. We later considered what happens when a chosen logo is paired with bold black wordmark text, tried brighter and darker colour directions, compared how the palette appeared on app/web icons in light and dark modes, and refined the wordmark. Its tone aimed for **clever, slightly rebellious and self-aware**, rather than generic AI SaaS copy.

**Domain reality mattered:** exact-name .com/.au options were researched for finalists in September 2026, but prices were point-in-time quotes, not guaranteed renewals or enduring availability. Later we selected and purchased **[roleriff.app](https://roleriff.app)** as the practical product home. Don't let a coveted .com automatically kill a better-fitting brand if a credible alternate domain works and the longer-term rights/risk picture is acceptable.

**What this case teaches:** Run more than one concept through a *mini brand*, not just a domain-availability spreadsheet.

### Tilfrd: a short coined name and a product identity that can expand

**[tilfrd.dev](https://tilfrd.dev)** became the brand for a platform focused on the boring, annoying operational parts of building SaaS products—starting with a waitlist module and expanding into reusable “bricks.” The name is compact and distinctive-looking, while the **brand story** does the work of explaining the product.

Its visual language developed into **tilfrd.** with a deliberate dot, a restrained dark/cream/coral palette and a voice that is **friendly, clever, lightly cheeky and plain-spoken**.

The lesson is that a name **does not have to literally describe every feature** if the brand and messaging quickly explain the value. But coined spellings impose a real cost: pronunciation, spelling after hearing it, and people typing the right domain must be tested, not assumed.

### When the product pivots, redo the *market* research

An earlier brand brief is not automatically authoritative after a scope change. In our work, **Tilfrd moved away from an earlier e-commerce QA/testing direction** into **a subscription collection of modular operational SaaS “bricks”**. That change altered both the product promise and the real direct/adjacent competitor set.

When a founder pivots, the agent should:

1. Record **OLD POSITIONING vs NEW POSITIONING**, customer, price and what is genuinely different.
2. Reclassify real direct, adjacent and substitute competitors using the new job-to-be-done.
3. Revisit whether the chosen/proposed name implies a feature no longer central to the product.
4. Re-run domain, naming collision and registration pre-screens if the target category/market changes.
5. Evaluate **KEEP**, **REPOSITION**, **EXTEND**, and **RENAME**—in that order of least disruption unless evidence argues otherwise.
6. If a rebrand wins, draft a domain, search, support, product copy and compatibility migration **plan**, not automatic deployment.
7. Preserve accepted historic decisions as **SUPERSEDED BY [new decision]** rather than deleting them.

**Brand architecture matters as much as renaming:** Bitzy Labs is the parent; RoleRiff and Tilfrd have independent personalities; GemAura is a platform/internal identity, with Isylon Gems and Ceylevia & Co as distinct storefront identities. Don't force every product/store/module to share one name or let an internal codename leak into customer messaging.

### Other Bitzy Labs naming patterns

We use **different naming mechanisms for different jobs** rather than force one house style:

- **GemAura:** an evocative master/product platform name that hints at the gem category while leaving room for visual/emotional association.
- **Isylon Gems and Ceylevia & Co:** separate customer-facing identities for different storefront roles instead of treating an internal platform name as every customer brand.
- **Control Central:** a functional internal/operational description when clarity matters more than memorability or consumer-facing distinctiveness.
- **Bitzy Labs:** the broader umbrella, leaving products free to have their own audience-appropriate identities.

These examples demonstrate the **observed structure of the naming portfolio**, not a claim that every historical name underwent the same documented shortlist, trade mark process or scoring. **Don't turn an inferred story about a name's origin into a claimed fact.**

### A lesson from an unfinished brand search

In another platform naming exercise, we maintained a **live naming board** containing the brief, current owner-approved territories, checked domains, near-neighbour/collision concerns and a **“rejected — do not recycle”** list. An idea could remain an *emotional benchmark* but be rejected as a registrable masterbrand. A catchy name could be killed for a confusingly similar nearby business, even with open domains.

We deliberately do not publish unlaunched finalist names or private collision research here. The reusable lesson is the **decision discipline**, not the candidate list.

## 3. Start with customer and brand personality

Don't ask “give me 100 startup names” as your first instruction.

Create a **one-page naming brief**:

| Field | Write down |
| --- | --- |
| Product | One sentence describing the real benefit, not architecture |
| Buyer / user | Who chooses it? Who uses it? Age, sector, geography as relevant |
| Frustration | What makes the existing experience feel awful? |
| Desired feeling | Relief, confidence, rebellion, delight, control, speed, trust, etc. |
| Brand personality | Choose 3–5 adjectives; avoid contradicting pairs |
| Not this | Words, styles, claims or impressions to explicitly exclude |
| Markets | Where will the product be sold now and later? |
| Expansion | Features or sectors the brand may reasonably grow into |
| Domain preferences | Preferred TLDs and acceptable alternatives |
| Budget | Initial purchase **and** renewal ceilings; brand/legal spend |
| Hard no-go | Risky collisions, hard-to-say words, misleading claims, inappropriate meanings |

### Different products need different emotional jobs

For one product the brief may be *unconventional but useful*. For another it may be *calm, friendly, reliable, no drama*. Your task is to capture the **feeling you want the customer to associate with the product**, not copy the style of a successful competitor.

**The Australian-vs-global test:** “Australian attitude” can mean straightforward help, warmth and capability **without** relying on novelty slang or stereotypical imagery. For a global product, check that the name works outside your home market.

## 4. Generate naming territories, not name spam

A naming territory is a **distinct strategic angle**. Ask AI for ideas inside several territories, then challenge the names that come out.

Examples of territories:

1. **Outcome/benefit:** relief, momentum, confidence, control.
2. **User identity/attitude:** independence, creativity, curiosity, getting on with it.
3. **Metaphor:** a pathway, a signal, a companion, a tool or place.
4. **Evocative compound:** two familiar ideas that create an unusual but natural association.
5. **Coined/altered form:** short and ownable-looking, but not random consonant soup.
6. **Functional/descriptive:** especially appropriate for internal services or technical modules.

Ask for perhaps 8–12 names across several territories as a starting batch. Review the *reasons*, not the volume. Expand only fruitful directions.

### Our repeated exclusions

- Generic software-name soup: endless **AI / Cloud / Stack / Hub / Flow / Web** suffixes without a strong reason.
- Unnecessary X/Q/Z substitutions merely to obtain an open domain.
- Tongue twisters, forced puns or a name that requires a speech to explain.
- Something that looks like a typo rather than a deliberate identity.
- A name that boxes a platform into the **first** feature when growth is plausible.
- Names that are unreasonably close to a competitor, especially in the same category.
- Names that imply false promises or inappropriate associations.

A descriptive name is not automatically bad; a coined name is not automatically clever. Judge fit.

## 5. Shortlist by behaviour and feel

Before trademark-heavy research, shortlist candidates with real-world human tests.

### The 10-second test

Say the name aloud once and ask another person to:

1. Repeat it without coaching.
2. Spell it without seeing it.
3. Guess how it sounds when spoken over the phone.
4. Say how it makes them feel.
5. Recall it after hearing several other options.

Try it with people who **don't** know your product. Don't teach them the intended meaning first.

### The product-fit test

- Does it sound like the right kind of company?
- Is it credible on a checkout or invoice, support email and app icon?
- Does the name let the product evolve?
- Does it avoid suggesting deception, scams or functions the product doesn't offer?
- Will it look sensible in a navigation bar and on a tiny mobile home screen?
- Is the first reaction good *without* a logo doing all the work?

Promote only the names that earn deeper investment.

## 6. Run the spoken, spelling and negative-meaning tests

Our naming boards explicitly consider:

- **Pronunciation:** easy when read, easy when heard; one obvious pronunciation helps.
- **Spelling:** how likely is the correct spelling in a search or email address?
- **Memory:** can it survive a conversation without a screenshot?
- **Phonetic neighbours:** two words that sound alike can collide even when they look different.
- **Double meanings:** sexual, rude, embarrassing, misleading or region-specific associations.
- **Negative phrases:** does the name accidentally imply a bad outcome?
- **Abbreviations:** what happens in headlines, hashtags, initials, app shortcuts?
- **International use:** check relevant languages, markets and native speakers rather than assuming an English-only review is sufficient.

A slightly unusual spelling may be worth it for a compelling product; document the trade-off rather than pretending there is none.

## 7. Investigate competitors, collisions and trade marks

**This is the most important distinction in the guide: an available domain does not establish that a name is safe to use or register.**

### Map the **real competitive landscape**, not just name collisions

A serious naming investigation starts with the **business idea**, because our name needs to make sense next to products customers might already pay for.

| Bucket | What qualifies | Agent evidence required |
| --- | --- | --- |
| **Direct competition** | Same/similar job-to-be-done, customer and purchase decision | Active product, customer, actual functionality and pricing if public |
| **Aligned / adjacent competition** | Overlapping buyer, workflow or distribution; could add our feature or already bundles part of it | What overlaps, why it may compete and current source |
| **Substitutes** | Agencies, DIY processes, spreadsheets, a platform bundle, in-house workflows | How customers solve the problem without buying us |
| **Brand/name collisions** | Exact, similar-looking, similar-sounding or misleadingly close identities | Actual use, jurisdiction, goods/services, confusion risk |

**Being a direct competitor does not mean their name is a conflict.** Likewise, a naming conflict need not be a direct competitor. The agent should deliver **two connected assessments**: market differentiation and brand-confusion risk.

**Agent research procedure:** search keywords related to *customer pain* and *jobs-to-be-done*; inspect live product sites, docs/pricing, app marketplaces and alternative lists; confirm what products *actually* offer, not vague teasers. Then check every serious candidate's exact name, common misspellings, speech-equivalent versions and industry-context queries across intended geographies.

Evidence record:

~~~md
| Product / company | Direct / Adjacent / Substitute / Collision |
| Official URL | Actual offer | Shared customer / workflow |
| Why it matters | Brand-name similarity | Geography |
| Evidence checked at | Risk | Open question |
~~~

**Real research can trigger a product pivot:** if a new/adjacent player already owns the job cheaply or a compelling whitespace emerges, revise positioning and re-run naming. Don't hide bad news to preserve a favourite name.

### Do an initial market collision search

For each serious finalist, search at least:

- exact name, close spelling, plurals and word breaks;
- names that **sound** alike;
- same/adjacent market categories (not just identical feature descriptions);
- web search, app marketplaces, relevant company directories;
- social handles and major developer/product communities;
- existing logos, wordmarks and slogans that might create confusion;
- jurisdictions you plan to serve.

Record actual business activity and category, not just an AI label of “clear” or “conflict.”

### Official Australian checks

- [IP Australia — Australian Trade Mark Search](https://search.ipaustralia.gov.au/trademarks): search exact and similar marks, classes and relevant goods/services. IP Australia itself cautions that a self-conducted search is not the equivalent of an examiner's determination.
- [ASIC — Business names vs trade marks](https://www.asic.gov.au/for-business-and-companies/business-names/register-a-business-name/business-names-vs-trademarks): registering a business name and owning trademark rights are **different things**.
- Consider a qualified trade mark professional for a consequential investment, disputed search or launch into multiple jurisdictions.

For the United States, the [USPTO's comprehensive clearance guidance](https://www.uspto.gov/trademarks/search/comprehensive-clearance-search-similar-trademarks) emphasises confusingly similar marks and **related goods/services**, not merely exact-word matches.

### Verify *business name availability* separately (ASIC)

Use [ASIC's official Business Names Register](https://www.asic.gov.au/online-services/search-asic-registers/business-names-register) to inspect existing registered holders and [ASIC's registration/availability instructions](https://www.asic.gov.au/for-business-and-companies/business-names/register-a-business-name) for the **Check business name availability** function. ASIC commonly reports:

- **Green:** name available for registration under its name tests.
- **Amber:** requires ASIC assessment; **do not** label available or cleared.
- **Red:** unavailable.

For coined or unusual spellings, **amber can mean manual review**. Record the exact query, returned status, date and link/screenshot where possible. Existing company or trading-name use may warrant further investigation even if exact registered business-name results appear empty. [ABN Lookup](https://abr.business.gov.au/) helps identify Australian business entities and relevant historical trading names.

**Business name availability is not ownership of the trade mark.**

### Verify trade marks separately (IP Australia)

Start with [TM Checker](https://www.ipaustralia.gov.au/tm-checker), then inspect [Australian Trade Mark Search](https://search.ipaustralia.gov.au/trademarks) for **exact and similar registered or pending marks**, common misspellings, similar pronunciation, word breaks and relevant **goods/services and Nice classes**. Review jurisdiction and actual commercial context. Later, assess confusingly similar logo directions too.

[IP Australia explains that searches do not guarantee a later registration outcome](https://www.ipaustralia.gov.au/trade-marks/search-existing-trade-marks). For consequential launch investment, unresolved overlap or overseas expansion, obtain appropriately scoped professional advice. If ASIC or IP Australia tools block programmatic access, the agent must return **NOT VERIFIED**, the **official portal URL**, proposed exact search term(s) and the minimum human action remaining.

**Always keep four statuses distinct:** DOMAIN STATUS · ASIC BUSINESS-NAME STATUS · TRADE MARK PRE-SCREEN STATUS · LEGAL CLEARANCE STATUS. None automatically proves another. A connected AI agent must not claim “trademark cleared” without a genuinely appropriate, documented legal conclusion.

### Collision status language

| Label | Meaning |
| --- | --- |
| **Not researched** | No reliable search performed |
| **Initial search only** | Some web/domain checks; legal status unknown |
| **Potential collision** | Similar name/use identified, requires further review |
| **Not recommended** | Material risk or poor strategic fit |
| **Professional review advised** | Legal clearance needed before investment |
| **Professionally cleared for stated scope** | Only if properly documented; never infer it |
| **Registered** | Only after registry confirmation; document jurisdiction/classes |

Do **not** write “trademark-safe” on the strength of an AI web search.

## 8. Treat domains like a long-term decision

An available-looking name can become financially inconvenient, confusing, or unattainable at the moment you are ready to launch.

### Check the full picture

- **Exact availability** at a registrar now, not an old snapshot.
- **Registration price vs renewal price**; discount first years can be misleading.
- **Premium/resale pricing** and any broker fees.
- **TLD trust and audience fit:** .com, .au, .com.au, .app, .dev, etc., based on product and geography.
- **Eligibility rules:** .au direct and .com.au have different rules; see [auDA](https://www.auda.org.au/au-domain-names/the-different-au-domain-names/au-direct-domain-names/).
- **Future protection:** whether acquiring matching domains later is affordable or necessary.
- **Email practicality:** domain spelling, ambiguity and risk of messages sent to a similar domain.
- **Portability:** who holds the registrar account, renewal reminders, DNS access and transfer capability.

### Automate live multi-registrar research (including Composio)

The founder shouldn't have to open 20 registrar tabs unless the tools are unavailable.

**Recommended agent order:**

1. Discover the **actual** connected domain lookup tools; check direct registrar actions and, if available, [Composio](https://docs.composio.dev/) for supported provider/app actions. Read input schemas; do not invent tool slugs, permissions or results.
2. Batch the surviving names/TLDs through supported bulk lookups (for example **GoDaddy**, **Namecheap**, **Spaceship**). Not every provider supports every suffix; preserve **UNSUPPORTED / NOT CHECKED** rather than inferring taken/available.
3. Record availability with the registrar, **time checked**, supported suffix and its **registration** and **normal renewal** prices, clearly identifying missing quote fields as **UNKNOWN**.
4. Compare real currencies, taxes, TLD eligibility and premium/resale price indicators. Beware limited first-year promotions and long-term renewals.
5. Include [Cloudflare Registrar](https://www.cloudflare.com/products/registrar/) in cost/operational comparisons when appropriate, but **do not assume Cloudflare offers the same live search API or every TLD**. Separate registrar ownership from Cloudflare DNS hosting.
6. Recheck the leading choice **just before owner-authorised purchase**. Registrar search does not reserve a name and provider prices change.
7. Suggest a **primary domain and only justified defensive domains**. Don't purchase all combinations.

Example evidence table:

| Name/TLD | Registrar | Live status | 1st year | Renewal | Premium/eligibility | Checked at | Source |
| --- | --- | --- | --- | --- | --- | --- | --- |
| [candidate.example] | [source] | AVAILABLE / TAKEN / UNKNOWN / UNSUPPORTED | [value or UNKNOWN] | [value or UNKNOWN] | [details] | [timestamp] | [URL/tool] |

**Observed practical lesson:** registrar tools that did not support an Australian extension could not establish whether it was available. Absence of a result was **not** permission to invent it. First-year deals were considered alongside real renewal exposure.

**Permission boundary:** Search and price comparison can be automated; purchase, renewal, transfer, billing, nameserver and DNS changes require explicit authorisation for the exact name and account.

### Keep exact status in the record

Never collapse these into “we have the domain”:

1. *Looked available in a search*;
2. *Quoted at a specific price and date*;
3. *Purchased/registered*;
4. *Verified as held in the correct registrar account*;
5. *DNS configured*;
6. *Website/email actually serving*;
7. *Redirects/renewal monitoring working*.

Keep account details and payment methods private. A domain purchase should be **owner-approved**, not a tool-side impulse.

### Practical TLD lesson

For RoleRiff we weighed .com/.au possibilities and ultimately adopted **roleriff.app** as a practical public-facing home. For Tilfrd, **tilfrd.dev** fits the builder-facing identity. Neither example is a universal instruction to choose those endings.

**Don't reject a great name solely because the .com isn't an easy buy.** But don't treat any random available TLD as a fix for unresolved trademark or customer-confusion risk.

## 9. Make finalists into actual brands

This stage separates a name that “sounds cool” from one that can support a business.

### Build a small finalist brand pack

For each of the top 3–5 names, create:

- **One-sentence brand thesis:** why this name matches the value and audience.
- **Tagline options:** direct, cheeky, and premium/serious versions.
- **Voice guide:** how the brand talks; what it never says.
- **Logo directions:** several genuinely distinct concepts, not 10 recolours of one generic mark.
- **Colour systems:** a few strategic choices tested with actual type contrast.
- **Wordmark:** real product name in app/web headers, icons and email identity.
- **Product mockups:** landing page, pricing, onboarding, dashboard, mobile icons.
- **Light and dark** presentation where relevant.
- **Realism test:** could a user trust and understand the product from its site, not just its logo?

Our RoleRiff finalist work deliberately explored **multiple logo directions and palettes per name**. Later we iterated on the relationship between the symbol's bright colour and the dark wordmark, tested icon variants, and chose a visual direction that actually worked in context.

### Don't let colour or a logo hide a naming problem

A sketch is not trade mark clearance. A highly polished logo is not proof of memorability, differentiation or purchase intent. Avoid copying an existing brand's distinctive symbol.

**This stage should be lightweight until collision screening is good enough.** Don't commission expensive final assets for every longlisted idea.

## 10. Score, choose, and preserve owner judgment

A weighted comparison keeps a strong-sounding suggestion from bypassing obvious problems. These **illustrative weights are a reusable template, not a claim that all Bitzy Labs names were scored numerically this way**.

| Criterion | Suggested weight |
| --- | ---: |
| Audience and emotional fit | 20 |
| Distinctiveness / brand story | 15 |
| Pronounceability and spelling | 15 |
| Memorability and visual versatility | 15 |
| Scales beyond initial feature | 10 |
| Practical domain/email economics | 10 |
| Brand voice/marketing flexibility | 10 |
| International/meaning suitability | 5 |
| **Total** | **100** |

Score each 0–5, then calculate a weighted result. Record evidence and uncertainty separately.

### Gates scores cannot overrule

**Fail or pause** a candidate if:

- it presents a material unresolved collision/trade mark concern;
- it carries a serious offensive/misleading meaning in the target market;
- required domains/identity cannot realistically be obtained at an acceptable cost;
- the founder and actual users consistently cannot pronounce, type or accept it.

A beautiful name that scores 92/100 can still be a bad choice.

### Founder judgment matters

AI rankings are *tools*, not authority. The founder should be free to reject the “highest-scoring” name for a concrete brand reason. Write that reason down so future naming rounds learn from it.

## 11. Maintain a living naming board

This is one of the most helpful safeguards against AI repeatedly offering the **same rejected ideas**.

Use a Notion database, GitHub Markdown table or spreadsheet. Keep one current status and historical dated entries.

### Suggested fields

| Field | Purpose |
| --- | --- |
| Candidate and phonetic spelling | What people will say/type |
| Product / audience | Which market and user it serves |
| Naming territory | Benefit, metaphor, attitude, coined, descriptive |
| Brand thesis | Why this word should make sense |
| Owner reaction | Strong yes, interesting, neutral, no |
| Status | Exploratory / shortlist / finalist / lead / rejected / adopted |
| Rejection reason | Brief and reusable: collision, vibe, spelling, cost |
| Do not recycle? | A clear yes/no |
| Collision research | Link, date, scope and unresolved risk |
| Domain snapshot | Exact TLD, availability, registrar, first-year/renewal, date |
| Voice & visual direction | Links to mockups or brand pack |
| Decision owner / date | Who can authorise purchase/registration |

### Keep the record honest

- **Current shortlist overrides older drafts**, but keep the historical reasoning.
- Mark rejected names **DO NOT RECYCLE**, rather than quietly deleting the evidence.
- A rejected name may survive as a *tone benchmark*; don't re-promote it without new justification.
- Distinguish **owner-approved territory** from **registered final identity**.
- Dates matter: “domain available on 23 September” is not proof it is available on 26 October.
- If a brand has not been selected, say **NOT SELECTED**.

This lets a new ChatGPT conversation or coding agent resume the naming work without rediscovering dead ends.

## 12. Approvals, purchases, registration and rollout

Naming spans creative work and real operational/legal decisions; keep these separate.

### Before spending

- [ ] Final spelling, pronunciation and market positioning accepted by owner.
- [ ] Relevant market searches completed; near names and trade mark risks evaluated.
- [ ] Professional clearance obtained where the stakes warrant it.
- [ ] Final domain availability and first-year **and renewal** cost verified.
- [ ] Registrant details and eligibility checked.
- [ ] Purchase budget approved.
- [ ] No unapproved domain, registrar, trademark or paid creative purchase.

### After owner approval

- [ ] Confirm registration succeeded and ownership is in the right account.
- [ ] Choose a canonical web domain and plan redirects if needed.
- [ ] Record exact adopted name and source-of-truth brand guide.
- [ ] Check core social handles and public naming consistency.
- [ ] Finalise vector assets and accessible light/dark brand applications.
- [ ] Update customer-facing website, navigation, support messages and metadata.
- [ ] Coordinate app-store/legal/customer communications if existing product is being renamed.
- [ ] Keep legacy/internal code identifiers until a **separately evaluated** migration is actually safe.
- [ ] Monitor renewals, DNS/email configuration and brand confusion.

**A rebrand is not permission to rename every database column, API route, worker, deploy target or code identifier.** Cosmetic and public identity changes must not break runtime compatibility.

## 13. Copy-paste naming prompts for ChatGPT

### Prompt A — Explore names without generating junk

~~~text
Act as a sharp but practical startup brand strategist for my own project.

PRODUCT: [one paragraph]
TARGET USERS: [...]
PROBLEM / EMOTIONAL PROMISE: [...]
BRAND PERSONALITY: [3–5 adjectives]
GEOGRAPHY: [...]
ROOM TO EXPAND: [...]
PREFERRED TLDS / MAX FIRST-YEAR + RENEWAL BUDGET: [...]
AVOID: [generic words, cliches, risky associations]
ALREADY REJECTED: [list with reasons]
EXISTING BRAND ARCHITECTURE: [...]

Do not jump straight to 100 random names.
1. Define 4–6 distinct naming territories and why each might work.
2. Propose 6–10 candidates per promising territory, each with one-line
   rationale, pronunciation, potential downside and fit.
3. Reject generic, hard-to-pronounce and nearly identical alternatives.
4. Separate creativity from facts: DO NOT claim domain, social handle,
   business register or trademark availability without live checks.
5. Suggest a shortlist of five maximum, explaining trade-offs.
6. Ask me to select emotional directions to explore more deeply.

Don't buy or register anything. Do not expose private product plans publicly.
~~~

### Prompt B — Qualify finalists with real research

~~~text
Evaluate these names for [PRODUCT]: [LIST].

Use current live research where tools permit. Date all findings.
For each name:
- say/pronounce/spell/memory tests to validate with real people;
- common meanings, negative associations and international risks;
- exact and similar use by software/businesses in adjacent categories;
- initial trademark search sources (not a legal clearance claim);
- exact domains, first-year and renewal prices, TLD eligibility;
- practical email/handle implications;
- possible brand voice, tagline and growth flexibility.

Record VERIFIED / ESTIMATED / UNKNOWN separately.
Use authoritative registry/registrar sources when possible.
Mark candidates as PASS, REVIEW or REJECT, with reasons.
Do not call a name trademark-safe or imply a domain has been purchased.
Output a shortlist and a reusable Notion/GitHub naming board update.
~~~

### Live registrar + official registry research — add this to any naming prompt

~~~text
For each current finalist, run read-only LIVE registrar searches using direct
supported GoDaddy, Namecheap and Spaceship tools, and/or Composio-discovered
provider actions where connected. Inspect schemas before executing.
Return a dated matrix with source, TLD support, availability, registration
and renewal price, currency, premium pricing, local eligibility and unknowns.

Also search the ACTUAL DIRECT and ALIGNED/ADJACENT competitors, not merely
the proposed name's web hits. Provide a real official product link and
evidence of its actual customer, features and market overlap.

Check ASIC business-name availability and registered-name search separately
from IP Australia TM Checker and Australian Trade Mark Search. Search
exact/phonetic/visual neighbours and relevant related goods/services.
Report precisely which checks actually ran and which are BLOCKED/UNKNOWN.
If a portal cannot be automated, give the official URL and exact term to
check; do not pretend legal clearance.

Use real findings to challenge positioning and detect necessary pivots.
Do not change names, buy domains, file business names/trade marks, incur
costs or edit any repo other than MY explicitly authorised project repo.
~~~ 

### Prompt C — Brand pack for true finalists

~~~text
Using the shortlisted names [LIST] and the accepted naming brief,
create for each:

- clear positioning and one-sentence rationale;
- three tagline directions and a concise brand voice;
- distinct art-direction/logo concepts;
- colour palettes with accessibility checks;
- wordmark ideas and light/dark usage;
- mockup briefs for landing, pricing, onboarding, app icon and mobile.

Do not clone competitor identities or use unlicensed assets.
Be candid if any name looks weak in real product contexts.
Prefer several substantially different directions over superficial recolours.
Do not claim visuals prove trademark clearance.
Keep this exploration separate from final production asset creation.
~~~

### Prompt D — Decision and project handover

~~~text
Create a naming decision record for [PRODUCT] from our actual research.

Include: accepted brand thesis; finalists; rejected/do-not-recycle
candidates with reasons; dated domain and collision findings;
unknown trademark/legal questions; owner decision and whether final;
canonical spelling, planned TLD and purchase status; chosen voice/visual;
follow-up actions and owner approval gates.

Do not confuse shortlist/lead with adopted/registered.
Mark expired research as historical, not current.
Use GitHub/Notion project records if available and authorised.
Otherwise produce a paste-ready Markdown handover.
Do not purchase, publish, register, deploy or alter provider settings.
~~~

## 14. Agent instructions for Codex and Claude Code

For a coding agent, product naming is mostly a **planning and documentation task**, not permission to start a rebrand migration.

1. **[Fork this guide](https://github.com/BitzyLabs/design_guide/fork) if you want your own editable copy**, or copy \`product_naming.md\` into **your own app repository**. The original **BitzyLabs/design_guide** remains **read-only** unless an explicitly approved contribution is being made.
2. Add a short note to your own \`AGENTS.md\` or \`CLAUDE.md\`:

~~~md
## Product naming
For product/brand/domain decisions, read ./product_naming.md.
Only edit files in THIS authorised app repository or my fork.
Treat BitzyLabs/design_guide as read-only upstream inspiration.
Do not buy domains, file trade marks, rename infrastructure, update DNS,
change production branding, publish or spend money without approval.
Separate creative candidates from verified availability/legal evidence.
Maintain a current naming board and a do-not-recycle list.
~~~

3. Give the agent an explicit product brief and a bounded task: e.g., **“research and compare five finalist names; prepare a decision memo, no code changes.”**
4. For any later **approved** rebrand, create a separate technical chunk: identify customer-facing strings versus compatibility-sensitive identifiers, review migration and rollback, and test the exact changes. See [project_mgmt.md](project_mgmt.md).
5. **Do not connect a write-capable agent to this upstream public guide just because you want it to read the Markdown file.**

If you prefer purely chat-based naming work, use [Prompt A](#prompt-a--explore-names-without-generating-junk) through [Prompt D](#prompt-d--decision-and-project-handover) with the current naming board.

## 16. Mistakes to avoid

| Temptation | Better rule |
| --- | --- |
| Ask AI for 500 names | Brief the customer/personality, then explore territories |
| Prefer a name because an AI scores it 95 | Use scores for comparison, not as a substitute for judgment |
| Repeat previously rejected names in every new chat | Current naming board plus do-not-recycle list |
| Call a name “available” after one web search | Separate market search, domain status and legal checks |
| Equate available .com with safe trade mark | Search similar names and related goods/services |
| Buy a cheap promotional domain without renewal check | Compare multi-year cost and eligibility |
| Fall in love with a logo before investigating collisions | Lightweight concept tests first; finalise after review |
| Choose a name that only fits version 1 of the product | Check adjacent use cases and expansion |
| Pick “unique” by removing vowels at random | Validate pronunciation, typing and memorability |
| Assume Australian slang works in every country | Test with the markets and speakers that matter |
| Publicly publish unlaunched naming shortlists | Keep internal candidates and research private until approved |
| Have an agent mass-rename code when public branding changes | Review compatibility and migrate in a separate authorised chunk |
| Point a write-capable agent at this guide's original repo | Fork or copy and verify writable target first |
